## What this project is

**fieldlog** is a Textual TUI + CLI for running catalogued network-diagnostic commands
(ping, curl, dig, traceroute, tcpdump, iperf3…) against a target and keeping a durable
per-target archive of every run — the raw log plus a JSON run record under `targets/<name>/`.
Recipes are YAML with variable templates (`$TARGET`, `$IFACE`, `$OUTDIR`…), extensible via
drop-in files and composable into ordered **chains**. The archive is the product: a week
later you can see exactly what was run against a host, when, and with what result.

## Strengths

Genuinely careful systems code — the parts that are easy to get wrong, and aren't:

- **The pty + `exec` design.** [`runner.py:161`](../fieldlog/runner.py#L161) `exec_form` execs a
  single simple command so the tool (not the wrapping `sh`) is the process waited on — the
  comment explains the real bug it fixes (dash dies of SIGINT while ping catches it and exits 0,
  so the shell's code was wrong). [`runner.py:186`](../fieldlog/runner.py#L186) `_make_ctty`
  sets a controlling tty so `/dev/tty` prompts (sudo, ssh passphrases) work. Both tested
  ([`test_controlling_tty.py`](../tests/test_controlling_tty.py),
  [`test_exit_codes.py`](../tests/test_exit_codes.py)).
- **Secret-safe prompt logging.** [`runner.py:106`](../fieldlog/runner.py#L106) `loggable_reply`
  writes a reply into the log only if it matches one of the prompt's *bracketed* choices
  (`[y/N]`); a passphrase becomes `(reply hidden)`. Real threat-model awareness, and tested.
- **Shell-safety validation of scope.** Allowlist regexes at
  [`recipes.py:70`](../fieldlog/recipes.py#L70) and the reasons/hints in
  [`recipes.py:79`](../fieldlog/recipes.py#L79) `is_blocked` refuse metacharacters with
  actionable messages.
- **Cross-process run numbering.** [`archive.py:248`](../fieldlog/archive.py#L248) reserves under
  `flock` on a *sidecar* lock (because `session.json` is swapped via `os.replace`,
  [`archive.py:227`](../fieldlog/archive.py#L227)), and the counter stores "highest handed out,"
  so a CLI run beside the TUI never reuses a number.
- **Report injection-safety.** [`report.py:143`](../fieldlog/report.py#L143) `_fence` picks a code
  fence longer than any backtick run in the tool output; table cells escape `|`
  ([`report.py:107`](../fieldlog/report.py#L107)). Rich markup is escaped everywhere data is
  printed ([`cli.py:75`](../fieldlog/cli.py#L75) and throughout).
- **One launch path.** [`launch.py:40`](../fieldlog/launch.py#L40) `plan_launch` is the single
  place both front-ends build command/env/paths, so CLI and TUI can't drift.
- **Comments explain *why*, not what**, and graceful degradation is real: one malformed drop-in
  is skipped with its line number, the rest of the catalog loads
  ([`recipes.py:510`](../fieldlog/recipes.py#L510)).

## Concrete improvements (ranked by impact)

### 1. `$IFACE` bypasses the shell-safety validation that `$TARGET`/`$HOST`/`$LHOST` get
[`recipes.py:79`](../fieldlog/recipes.py#L79) `is_blocked` validates target, dns, and lhost but
has no `IFACE` branch; [`state.py:263`](../fieldlog/state.py#L263) substitutes it straight into
the command. Confirmed by dry-run:

```
$ fieldlog run ping/sweep 192.168.1.5 -i 'eth0;id' --dry-run
  Command:     ping -c 1 -W 1 -I eth0;id 192.168.1.5      # the ;id would execute
$ fieldlog run ping/sweep '192.168.1.5;id' --dry-run
  Error: target has unsafe characters (;)                 # same ; in the target is refused
```

The interface and lhost are even set from **one** `T` field
([`app.py:659`](../fieldlog/app.py#L659)) — lhost is checked, interface isn't. It's
operator-supplied (footgun, not remote RCE), but it's the one gap in an otherwise-complete
validation story. **Fix:** an `IFACE` branch in `is_blocked` reusing `_UNSAFE_SCOPE`, plus a
param test beside [`test_scope_chars.py`](../tests/test_scope_chars.py). ~5 lines.

### 2. No CI, no codified lint/type config
Despite `# noqa`/`type: ignore` markers in [`app.py`](../fieldlog/app.py),
[`recipes.py`](../fieldlog/recipes.py), [`report.py`](../fieldlog/report.py) implying ruff/mypy
are run locally. For a pipx-installable OSS tool this is the biggest process gap. 138 tests run
in ~5s — cheap to gate on 3.11–3.13, plus `[tool.ruff]`/`[tool.mypy]` in
[`pyproject.toml`](../pyproject.toml) so contributors get the same checks.

### 3. `app.py` is a 3003-line monolith
49% of the codebase, holding ~11 modal/widget classes plus the App. Extract modals
(`HelpModal`, `TargetModal`, `RecipeManagerModal`, `CloseJobModal`, `QuitConfirm`,
`PaletteModal`) and small widgets into `fieldlog/modals/` and `fieldlog/widgets/`, and move the
pure top-of-file helpers ([`app.py:183`](../fieldlog/app.py#L183) `tokenize`,
[`app.py:209`](../fieldlog/app.py#L209) `arg_groups`) into a util module. Navigability/testability
win; no behavior change.

### 4. The arg-band parser is untested
`tokenize` and `arg_groups` ([`app.py:183`](../fieldlog/app.py#L183),
[`app.py:209`](../fieldlog/app.py#L209)) drive what the operator sees before hitting Enter, and
have zero tests. They're pure functions — easy, high-value unit tests.

### 5. Jobs can orphan on TUI quit
On `self.exit()` workers are cancelled; `_run` catches `CancelledError`
([`app.py:2906`](../fieldlog/app.py#L2906)) but doesn't kill the group, and `run_job`'s finally
only `proc.terminate()`s the direct child ([`runner.py:344`](../fieldlog/runner.py#L344)) — a
`sh -c` pipeline's `setsid`'d children survive. `QuitConfirm` warns but doesn't reap. Consider
`killpg` on cancellation. Minor; only bites with long jobs at quit.

### Minor
An empty primary log whose mtime doesn't advance could fall out of the artifacts list
([`archive.py:131`](../fieldlog/archive.py#L131) records only `changed_since` entries) —
cosmetic, since the report still finds the log via `resolve_log`. Low confidence (O_TRUNC usually
bumps mtime). Repo hygiene is otherwise clean — `.gitignore` already handles `targets/*` operator
data and `*:Zone.Identifier`.

## Innovative ideas (grounded in what's here)

1. **Structured findings / parsers — the north star.** Already the README's "Planned"
   ([`README.md:501`](../README.md#L501)), and the schema is ready: records already carry
   `exit_code`, `artifacts`, `duration`. Add an optional per-preset `parse:` (regex or named
   parser) that extracts a one-liner — "4/4 replies, 0.02 ms", "cert expires in 12 d",
   "200 in 340 ms" — stored on the record as `summary` and shown in `history`, `report`, and the
   TUI tab. Turns an archive of *logs* into an archive of *answers* without changing the run
   model. (Orthogonal to diffing/repeat/JSONL, which are out of scope.)
2. **A `doctor` / catalog preflight.** `is_blocked` already computes, per recipe, the missing
   binary (+`KNOWN_INSTALL` hint) or missing var. Aggregate it into one command that reports the
   whole catalog's runnability against the current scope. **✅ Implemented — `fieldlog doctor` / `check` · `d1bd254`.**
3. **Per-recipe success semantics.** A preset field like `success: [0, 1]` would let
   `history`/`report` color a run correctly instead of flagging expected non-zero exits as
   failures — a small schema add that fits the existing exit-code care.
4. **HTML report export.** `render_report` is already a pure function
   ([`report.py:252`](../fieldlog/report.py#L252)); a `report --html` (self-contained) would make
   field reports shareable without a Markdown viewer. Optional — only if sharing is a goal.

5. **Serve-and-log: HTTP/HTTPS servers as recipes** *(field idea, 2026-09-15 — verified
   end-to-end, see below).* A recurring field need is to stand up a throwaway HTTP or HTTPS server
   — catch a callback, receive an upload, host a payload — and see exactly what hit it. fieldlog is
   a natural home: the server is just a long-running recipe, and every request lands in the archived
   log under a run record with timings and exit status.

   - **Long-running / non-terminating servers already work** — no runner change needed. Verified:
     `python3 -m http.server` launched through `fieldlog run` kept running (did not self-terminate),
     streamed each request line live to both the pane and the raw log, and on Ctrl+C wrote a normal
     run record. It's the same "runs until you stop it" model as the Wireshark GUI recipe. The one
     rule is the same too: **don't set `--timeout` on a server** (it would kill it). With a
     `SIGINT`-to-`sys.exit(0)` handler the stop is clean (`exit_code: 0, interrupted: true`) — the
     same tidy shape the README describes for `ping`.

     ```yaml
     recipes:
       - id: http
         bin: python3
         presets:
           - id: serve                       # requests stream to the log; Ctrl+C stops it exit 0
             flags: >-
               -c "import http.server,signal,sys;
               signal.signal(signal.SIGINT, lambda *_: sys.exit(0));
               print('Serving HTTP on :8000', flush=True);
               http.server.HTTPServer(('0.0.0.0',8000), http.server.SimpleHTTPRequestHandler).serve_forever()"
     ```

   - **The `openssl` → HTTPS handoff is a textbook use of the chain feature.** Verified: a two-step
     chain where step 1 writes a self-signed cert into the chain's *shared* `$OUTDIR`, and step 2
     loads that same cert and serves TLS. `curl -k` got HTTP 200; the archive recorded both steps
     plus the chain summary. This is exactly what shared-`$OUTDIR` chains are for — one artifact
     produced by a step, consumed by the next.

     ```yaml
     recipes:
       - id: certgen
         bin: openssl
         presets:
           - id: selfsigned                  # -nodes + -subj keep it non-interactive
             flags: "req -x509 -newkey rsa:2048 -nodes -keyout $OUTDIR/key.pem -out $OUTDIR/cert.pem -days 1 -subj /CN=$HOST"
       - id: https
         bin: python3
         presets:
           - id: serve
             flags: >-
               -c "import http.server,ssl,signal,sys;
               signal.signal(signal.SIGINT, lambda *_: sys.exit(0));
               ctx=ssl.SSLContext(ssl.PROTOCOL_TLS_SERVER);
               ctx.load_cert_chain('$OUTDIR/cert.pem','$OUTDIR/key.pem');
               h=http.server.HTTPServer(('0.0.0.0',8443), http.server.SimpleHTTPRequestHandler);
               h.socket=ctx.wrap_socket(h.socket, server_side=True);
               print('Serving HTTPS on :8443', flush=True); h.serve_forever()"
     chains:
       - id: tls-serve
         name: "self-signed cert, then HTTPS"
         steps: [certgen/selfsigned, https/serve]
     ```

   - **Caveats for shipped recipes:** (a) `openssl req` must be non-interactive — `-nodes` (no
     passphrase) and `-subj` (no prompts). (b) Give the server a `SIGINT` handler so Ctrl+C exits 0;
     left uncaught it exits 130 (still recorded correctly, just noisier). Ship both beside the
     Wireshark example in [`recipes.d/examples.yaml`](../recipes.d/examples.yaml).

   - **Why it strengthens idea #1:** the request log is plain text today, so this is the clearest
     motivation for a `parse:` field — turning `"GET /x HTTP/1.1" 200` lines into structured
     findings (method, path, status, client) would make "what hit my server, and how did it answer"
     readable straight from `history`/`report` without opening the log.
